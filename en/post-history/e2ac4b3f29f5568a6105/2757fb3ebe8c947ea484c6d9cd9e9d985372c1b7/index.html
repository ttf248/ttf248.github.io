Historical Issues

Also addressed the git folder permission files encountered after reinstalling the system: Fatal error “unsafe repository (’/home/repon’ is owned by someone else)” Most suggested solutions online originate from stack overflow:

  1. Add trust to the repository directory: git config --global --add safe.directory /home/repon
  2. Manually modify the configuration file .gitconfig, specifying the directory to add trust After using these methods, repository updates were normal, but numerous warning messages appeared in the console every time git pull was executed, indicating owner errors.

Reinstalling the System on a Desktop Machine

The machine hadn’t been reinstalled for a long time, and the system partition was filled with a massive amount of garbage files, leaving me no choice but to take some time to reinstall it. I ran into this permission issue again, and previous scripts wouldn’t run because the permissions were incomplete.

Using the new approach, I simply added *, which automatically trusts all directories for git.

I suspect it’s a user permission issue, or perhaps everyone hasn’t gotten used to the fact that Windows also has similar commands like chown to modify folder owners. Of course, if you have only a few directories, you can manually change the owner. However, this work computer has domain information added, and I’m not sure whether it’s due to an anomaly in the company’s deployed domain or an abnormality in the local system settings. In the user list, I couldn’t find the user used for login. Finally, I resolved it by processing through the command line.
