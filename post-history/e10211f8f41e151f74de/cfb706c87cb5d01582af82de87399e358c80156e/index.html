如果我已经知道该选哪个图像模型、用哪一种搜索索引、怎样让显卡跑起来，我当然能写出一条很专业的提示词。

可我遇到的问题，恰好发生在这些知识之前。

我有一个主要在 Windows 上运行的项目，电脑里有一张 RTX 3060。我想让照片变得好找：输一句话，找到内容相关的图片；给一张照片，找出相似内容；按地点和人物把照片聚起来。最好每天在后台把新增照片处理掉，能看到任务记录，失败了能查到具体卡在哪里。

这已经是一个很明确的愿望。接下来到底应该叫语义检索、图像嵌入、OCR，还是人脸聚类，应当允许我暂时不知道。

我缺的是那座桥

过去找人开发一个功能，并不要求委托人先说出数据库索引和图像推理框架。理解业务以后，把愿望翻译成工程问题，是专业工作的一部分。

我期待 AI 也承担这一段。

它可以先读项目，弄清楚现有界面、服务、数据库和任务机制；再去查当下有哪些现成实现，哪些适合 Windows，哪些只能在另一套部署环境里跑。材料读过以后，给出一条有理由的路线，做一个小样验证，再继续推进。

如果每到一个陌生领域，它都反过来问我“你打算采用什么技术栈”，这份研究工作就又回到了我手里。即使最后代码写得很快，我仍然得先学会怎样指挥它。

这也是我对一些国产 AI 产品感到别扭的地方。它能很顺畅地解释已有概念，可任务一旦需要查英文文档、顺着 GitHub 找实现、读版本变更，主动探索就容易停下来。有时它给我的，是一套在任何电脑上似乎都能成立的架构，里面没有我的 Windows，也没有我的显卡。

我自己在部分境外产品上，更容易得到继续搜索、继续读仓库、尝试修正的体验。这种使用感受值得认真对待，但它还不足以变成一张“国产模型都不会、境外模型都会”的成绩单。比较时要看具体产品、具体工具权限和同一个任务，不能让产地替所有差异作答。

尤其“能不能访问全球资料”，至少包含几件事：模型会不会寻找证据，产品有没有搜索和浏览工具，运行环境能不能连接目标网站，以及助手被允许读写哪些东西。模型参数本身不会替产品建立一条网络通道。

用户用起来感受到的是整个系统。一个环节没有接上，最后表现出来的就是“它做不了”。产品不能只拿模型会多少知识来解释这种落差。

一个相册愿望，里面其实藏着几种不同的搜索

先把我要找的东西讲清楚，很多技术选择就不会混在一起。

我会怎样描述 系统需要理解什么
找到那张写着发票号码的照片 读出图中文字，再匹配文字；这是 OCR 与文本检索
找到傍晚海边有人散步的照片 比较一句话与画面内容的关联；这是语义检索
找到和这张照片相似的内容 以图片作为查询，寻找视觉上相关的照片
把同一个人的照片放在一起 检测人脸并聚类，允许人纠正分组和姓名
找出某次旅行的照片 利用已有时间、GPS 与地点信息组织照片

这些能力可以在同一个界面里出现，底下却未必由同一个模型完成。OCR 能读路牌，不代表它理解一张没有文字的风景；语义搜索能找“海边”，也不能保证精确找到某个发票号码。

地点同样有边界。读取照片里的经纬度，与从画面猜它在哪里，是两种难度完全不同的任务。缺少 GPS 的照片可以等待补充，不能为了让相册看上去整齐，就把猜测保存成确定地点。

“以图找相关内容”还有一个需要说明的范围：在自己的图库里找相似照片，与上传图片到互联网寻找出处，是两种产品行为。按这个本地相册的目标，我会先验证前一种；跨网搜索会把什么传出去，应当另行说清楚。

这些区分不需要我在开口前就知道。助手应该从自然语言里把它们识别出来，只在确实影响选择的地方向我确认。

找到了项目，也要继续读下去

顺着这些需求搜索，很快会碰到 LibrePhotos 和 Immich。两者都已经把相册、人物、地点与内容搜索做成了系统。我并不需要先从一堆最底层的库重新发明一遍相册。

但搜索结果里出现两个名字，距离“适合我的项目”还很远。

LibrePhotos：先验证本机目录管理

官方已提供 Windows 独立版，适合个人电脑上的图库；语义搜索、相似图片、人物与地点管理可以作为需求样本。重点核实功能开关、当前版本和现有项目怎样接入。

Immich：先看完整相册服务是否合适

仓库列有照片视频管理、移动端备份、地图、人物与 CLIP 搜索。它值得作为完整服务评估；若要只借用其中一段能力，仍需考察接口、部署与维护成本。

例如，我原先猜测“语言大概率是 Python”，因为本地模型与图像处理经常会用到它。实际读到 LibrePhotos 的 Windows 安装说明后，会发现独立包已经把服务、网页、后台工作进程和相关依赖装进同一个目录，使用者不必先手动安装 Python、Docker 或数据库服务器。这个版本主要面向个人电脑上的个人图库。

这就改变了第一步：先拿小图库验证一个现成系统，可能比立即设计 Python 服务更划算。

不过，完整相册能跑起来，只能证明它可以独立使用。我正在改的是另一个已有项目，界面、权限、数据归属和任务入口能否衔接，还得读那个项目的实际代码。本篇没有拿到那个项目，当然不能替它宣布“已经适配”。

这正是主动调研的价值。找答案的过程中，最初设想可以被更好的材料改变。只沿着我随口说出的“Python”继续补方案，反而可能把我锁在一个并不必要的前提里。

显卡也是如此。LibrePhotos 当前的运行环境说明区分了几条路径：原生 Windows 可以通过 Direct3D 12 使用 GPU；文档所述 Docker Desktop、WSL2 环境下的那条 WebGPU 路径则运行在 CPU 上。Immich 的机器学习加速说明走另一套配置，Windows 服务器通过 WSL2，NVIDIA 可选 CUDA，并有驱动等条件，文档仍提示兼容性限制。

同样是“有一张 NVIDIA 显卡”，部署选择就可能让答案完全不同。助手需要继续核对日志里的执行后端，观察显卡是否真正参与计算，测一小批照片的耗时与资源占用。没有这些结果，就只能说有候选路线，不能许诺“3060 肯定流畅”，更不能凭空给出处理速度。

每天替我做，才是功能完成的地方

把一张照片跑通，容易让人觉得大部分工作已经结束。可我真正想省掉的是第二天、第三天还要继续做的事。

新增文件怎样发现？今天失败的一张，明天会不会永远被跳过？模型换了，旧索引怎么办？一次任务中断，是从头重来，还是接着处理？

这些问题决定它能不能从一次演示变成每天可用的功能。

现成项目也能提供具体参照。LibrePhotos 的自动扫描文档已经支持在应用里设置每日等扫描计划，默认关闭；扫描按规则处理新增或变化文件，正在排队或运行的扫描不会重复叠加。任务系统文档则说明了队列、运行进度与起止时间等记录。这些都是调研时应该看到的能力，不能一边建议使用成熟项目，一边又要求从零写一套定时脚本。

如果现有项目仍需自己的任务中心，我希望它至少能把一次运行解释成下面这样。这是设计用的假设快照：某次扫描发现 12 张待建索引的图片，已成功 8 张、失败 1 张，另有 3 张待处理；完成率只按成功图片计算，为 66.7%。它不连接后台，也不是本机实测。

看板只是入口。点进失败记录，应当能知道是哪张图片、哪个步骤、发生了什么错误、已经重试几次；普通用户能读懂原因，需要排查的人能进一步看到日志。总进度停在一个百分比上，却说不清为什么停，仍然是在要求用户替系统值班。

数据库里的分析结果和原始照片也需要分开。人像分组、向量与识别文字可以先存在索引库；是否写回照片或旁边的 XMP 文件，是另外一个选择。LibrePhotos 的元数据设置也明确区分只保存在系统内、写旁车文件和写入原文件，默认不写回。一个“更新元数据”的模糊说法，不足以授权程序改动所有原片。

本地处理也要看清保存了什么

LibrePhotos 的 OCR 文档说明，开启后会把识别出的文字以明文保存在数据库中，证件、信件和票据也可能被读出来；关闭识别并不会自动清除已有文字。模型在本地运行，仍需要理解索引库和备份里留下了什么。

这些细节不该成为拒绝推进的理由。它们应当进入方案和验收，让人能够放心地把日常任务交出去。

我愿意说清目的，不想先拿一张资格证

最终我仍然会提供材料：项目在哪里，照片大致是什么，愿不愿意引入 WSL2，哪些数据可以离开本机，期望怎样看到结果。这些信息别人没法替我猜。

但候选项目在哪里、文档怎么读、不同版本的限制是什么、哪个模型负责哪一段，应当由助手主动研究。查不到就换一条可用来源，连不上就把具体障碍说明白；读到不适用的条件，就修正方案。已经有足够信息完成的部分，继续往前做。

我衡量它有没有帮上忙，也会因此变得具体：能否用一个小图库证明文字搜索与画面搜索各自可用，新增照片能否进入下一次任务，失败能否追溯，原片有没有被改动，所谓显卡加速是否真的发生。几十个库名并不能代替这些结果。

AI 最吸引我的地方，是它有机会把不同领域之间的距离缩短。不会写图像模型的人，也可以提出一个值得实现的相册需求；不认识开源项目的人，也可以在助手帮助下找到合适的起点。

我连库名都不知道，才需要它去找。等我把答案都查好了，再把提示词写得像一份开发设计书，这份帮助就已经来晚了。
