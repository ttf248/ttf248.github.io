系统服务之间的数据同步近期做了一轮改动，接口流量一上去就开始频繁报死锁。同事拉出 InnoDB 日志排查，发现罪魁祸首不是常见的行锁加锁顺序不一致，而是 MySQL 的间隙锁（Gap Lock）。

平时业务里直接写 MySQL 调优的场景不算多，借着这次线上排查，把间隙锁的底层原理、主流大厂为什么普遍切到 RC 模式，以及放到我们金融/券商系统里到底该怎么选型，一次性理顺。

间隙锁到底锁的是什么？

在 InnoDB 默认的隔离级别 RR（Repeatable Read，可重复读） 下，行锁锁住的并不只是表里已经存在的记录。

假设一张表的主键或二级索引里目前只有 id = 10 和 id = 20 两条数据，中间 (10, 20) 这个开区间其实是空的。如果你在 RR 模式下执行范围当前读（如 WHERE id > 10 AND id < 20 FOR UPDATE），或者对一条根本不存在的记录加锁（如 WHERE id = 15 FOR UPDATE），InnoDB 会把 (10, 20) 这段空档锁起来——这就是间隙锁（Gap Lock）。

当行锁（Record Lock）与它前面的间隙锁合体，形成左开右闭区间 (10, 20] 时，就是常说的 Next-Key Lock（临键锁）。

为什么数据同步一并发，就会因为间隙锁死锁？

间隙锁最反直觉的规则是：间隙锁之间是相互兼容的。 两个事务可以同时拿到 (10, 20) 的间隙锁，互不阻塞——因为间隙锁的唯一目的是“阻止别人往这个缝隙里插入新记录”，并不阻止别人也来守着这个缝隙。

但在数据同步最常见的“先查记录存不存在，不存在就插入”的逻辑里，这个兼容特性会直接制造经典的环路等待：

sequenceDiagram
    participant T1 as 事务 A
    participant DB as InnoDB 间隙 (10,20)
    participant T2 as 事务 B

    T1->>DB: 查询 id=15 FOR UPDATE（不存在）
    Note right of DB: 获取间隙锁 (10,20)
    T2->>DB: 查询 id=15 FOR UPDATE（不存在）
    Note right of DB: 同样获取间隙锁 (10,20)（兼容）
    T1->>DB: INSERT id=15（申请插入意向锁）
    Note right of DB: 被 T2 间隙锁阻塞
    T2->>DB: INSERT id=15（申请插入意向锁）
    Note right of DB: 被 T1 间隙锁阻塞，触发死锁

低并发时，两个同步任务很难撞在同一毫秒、同一个空区间里；一旦批量同步流量上来，死锁就会成片爆发。

MySQL 为什么要设计这么“麻烦”的锁？

既然这么容易诱发死锁，InnoDB 为什么默认在 RR 模式下开启间隙锁？核心原因有两个：

  1. 防“当前读”的幻读（Phantom Read）：普通 SELECT（快照读）靠 MVCC 读取历史版本，不会受新插入数据干扰；但 SELECT ... FOR UPDATE、UPDATE、DELETE 属于当前读，必须读最新提交的数据。如果不锁住间隙，事务 A 在同一事务内两次范围更新之间，事务 B 偷偷插进一条满足条件的新记录，事务 A 就会看到凭空多出来的“幻影行”。
  2. 历史上的 Statement Binlog 主从一致：早期 MySQL 主从同步默认用 Statement 格式（记录原始 SQL）。如果主库执行范围更新时不锁间隙，并发插入的新行先提交并写入 Binlog，传到从库重放时就会把新行也一并改掉，造成主从数据不一致。

怎么关闭间隙锁？主流大厂为何偏爱 RC？

关闭间隙锁最彻底的方式，是将事务隔离级别从 RR 调整为 RC（Read Committed，读已提交），并配合 binlog_format = ROW（现代 MySQL 默认项）。

切到 RC 之后，会发生三个关键变化：

  • InnoDB 取消了普通查询与更新中的间隙锁（仅在外键检查和唯一索引冲突校验等极少数场景保留），并发写入的死锁概率断崖式下降；
  • 扫描过程中，不符合 WHERE 条件的记录锁会尽快释放，而不必等到整个事务结束；
  • ROW 格式 Binlog 记录的是每行实际变更结果，主从同步不再依赖间隙锁保序。

因此，国内绝大多数高并发互联网大厂的常规业务库，默认规范都是 RC + ROW Binlog——大多数短事务接口根本不需要在同一个事务里反复读取两次全量快照，用放弃“可重复读”换取高并发与低死锁，是一笔非常划算的买卖。

金融与券商系统：按链路拆开选，不能一刀切

但回到券商这类金融行业系统，架构选型不能简单照搬互联网的“全员 RC”，而应该按业务链路的真实一致性诉求拆开：

高并发交易 / 资金 / 数据同步链路
  • 推荐方案：RC + ROW Binlog
  • 防错手段：精准主键/唯一索引 + 悲观行锁或乐观锁（CAS 版本号）+ 唯一键防重幂等。
  • 原因：资金扣减和同步写入最怕死锁和并发超卖，靠精确行锁和条件更新（如 balance >= amount）比靠间隙锁更安全、吞吐也更高。
日终清算 / 对账 / 风控报表链路
  • 推荐方案：RR（隔离于只读从库或独立快照库）
  • 防错手段：一致性快照读，与在线交易写入链路物理隔离。
  • 原因：清算与对账需要在一个批次内多次汇总的结果严格一致，不能前脚算完总账、后脚拉明细时因为中途插入新流水而对不上数。

线上排查与改造的实用防线

如果你正在处理类似的数据同步死锁，在决定是否全局切换 RC 之前，有四条工程动作可以立刻落地：

  • 消除空范围加锁：能用单条幂等语句（或先按主键路由分片，确保同一批 key 只由固定消费者顺序处理）就不要并发“先查空再插”。
  • 把非数据库操作移出事务：RPC 调用、序列化、外部接口校验全部放到事务外，缩短持锁窗口。
  • 核对执行计划：通过 EXPLAIN 确认同步 SQL 精准命中索引，防止索引失效导致锁升级为全表间隙锁。
  • 加上压测与重试：高并发下的锁冲突很难靠代码审查完全看出来，上生产前最好用压测工具提前把锁竞争打出来（连接模型与压测工具选择可参考wrk 与 JMeter 怎么选），同时为幂等同步任务配置有限次数的死锁退避重试。
