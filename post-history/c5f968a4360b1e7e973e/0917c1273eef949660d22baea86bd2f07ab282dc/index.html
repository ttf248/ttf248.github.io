模型不会判断下一步，我替它写分支；不会检查结果，我再接一个校验节点；工具报错不知道怎么办，就补几条重试规则。这样当然能把事情跑通，但每接一根线，我都在想：这些工作，到底应该由谁来承担？

当模型能力不足时，工作流是一种很实用的办法。人把任务拆细，把不稳定的判断包进确定的步骤里，最后得到一个能用的应用。可模型逐渐能读材料、调工具、看错误、修代码以后，原先替它搭的那些补丁，就应该有机会被删掉。

我对下一代 AI 产品的期待很直接：目标、资料、权限和验收条件已经说明白，就请把任务做完。用户不应该还得先学会怎样替模型安排一整天的工作。

扣子的调整，不能替所有工作流宣判

先把这次新闻说准确。火山引擎发布的是扣子企业版分阶段下线公告，不是整个扣子产品立即消失。

公告涉及的范围 关键日期与安排
企业标准版、企业旗舰版新客户购买 2026 年 11 月 30 日起停止新售
在火山引擎购买的旧个人进阶版、旧企业版、旧团队版 2026 年 12 月 31 日全面下线，超期未使用部分按公告退款
新版企业套餐 服务到期日不晚于 2027 年 12 月 31 日

公告给出的原因是产品整合安排。把它直接解释成“字节已经证明工作流没有前途”，就走得比材料远了。产品商业化、套餐与交付方式的变化，和一项技术路线是否失去价值，不是同一张投票。

但这件事确实提醒我，应该重新算一笔维护成本。

有些流程在表达真实业务：报销需要谁审批，金额如何计算，哪个系统能写入，什么记录必须留存。这些约束不会因为模型更会推理，就自动失去意义。

另一些流程却主要是在补模型的短板。为了让它读懂一个网页，预先把每种结构拆开；为了让它生成一个可用文件，把许多格式细节外包给定制节点。模型升级以后，如果这些结构仍要求用户继续维护，原本帮助落地的产品就可能变成一笔越来越难解释的负担。

我愿意继续为真实业务规则付出精力，却不想永久替一个已经会做的模型重复写说明书。

用户不该一直担任运行时

工作流与 Agent 的差异，不在界面有没有连线，也不在产品名称里有没有“智能体”。

Anthropic 的工程说明提出了一个实用区分：工作流主要沿着预先写好的路径协调模型和工具；Agent 则由模型根据任务进展动态决定过程与工具使用。实际系统可以混合两种方式。

我更关心这种差异在失败时会怎样表现。

固定流程遇到网页结构变了，常常需要维护者回来改一个节点。能够承担任务的系统，则应该先读懂新的返回内容，判断原办法为什么不行，换一条有根据的路径，再检查是否达到了目标。

这不等于它可以随便绕过权限或猜一个答案。它需要的是在已授权范围内处理正常的复杂性，而不是每碰到一次报错，就把报错原封不动递给用户。

产品和开源项目，正在补不同的那一段

把所有相关工具堆在一起，很容易误以为谁节点更多，谁就更接近下一代产品。实际上，它们承接的是不同责任。

产品 更接近哪一类工作
Claude Code 在开发环境里理解项目、操作文件和工具，推进编码任务
Codex CLI 在本地项目中读取、修改与运行代码，处理受约束的工程任务
Cursor Agent 在编辑器中结合代码搜索、修改、终端和浏览器推进任务
Manus 的浏览器能力 通过授权浏览器操作网页，把部分网页工作交给系统执行

这张表按官方定位归类，不是我做过统一实测后的排名。尤其网页操作里有登录状态、界面变化和外部副作用，厂商文档也保留了监督与授权要求。能演示完成一次，与日常任务中可以放心连续交付，是两道门槛。

开源与源码可见项目，更多是在把执行系统拆成可以自行组合的部件：

项目方向 可以从哪里看起
应用与业务集成 Dify 组织模型应用、知识检索和工具流程；n8n 连接业务系统，也容纳 AI 判断与自动化
有状态的执行与任务组织 LangGraph 管状态、持久化和执行控制；Deep Agents 在其上提供规划、文件上下文等任务能力
工程任务与运行环境 OpenHands 的 Agent Canvas 与相关运行后端管理编码 Agent；DeerFlow 组合工具、记忆、技能和沙箱推进较长任务
网页行动能力 Browser Use 让模型操作浏览器，是执行环节的一种选择，不能单独替代整个业务系统

这些项目本身就说明，模型更强并没有让工程系统消失。状态怎样保存、失败怎样恢复、成果在哪里检查，仍需要有人做。区别在于，哪些细节应由开发者在产品里一次解决，哪些真有必要交给每个最终用户重复搭建。

“能在 GitHub 看见源码”也不等于所有商业使用都没有附加条件。Dify 的许可有额外条款，n8n 在仓库中明确使用 fair-code 及相应许可。选作商业底座时要读具体许可，而不是只看“开源”二字。

模型还在进化，系统也得学会接住它

如果问现在主流路线走到哪里，我更愿意沿着能力的来源去看，而不是排一张过几周就会变化的榜单。

基础训练仍然决定模型看过什么、能表示什么。 更好的数据、训练方式与计算效率，继续抬高理解和生成的底座。但知道很多事，与遇到一个新任务时能选对行动，仍有距离。

后训练在加强判断与可验证的推理。 DeepSeek-R1 的公开材料展示了强化学习、冷启动数据与蒸馏等做法。这是理解路线的一个公开例子，不是把一个较早发布的模型写成今天所有能力的终点。代码、数学等容易检验的任务尤其适合围绕结果改进训练，开放世界里如何评价“做得好”则更复杂。

推理时计算，让同一个模型在困难任务上多做工作。 OpenAI 的推理模型说明把内部推理与推理强度作为产品能力的一部分。多想一些可以改善复杂任务，但也增加时延和成本；没有工具、没有正确材料时，多花计算也不会自动变出缺失的事实。

执行系统在处理上下文、工具和长任务。 LangGraph 与 Deep Agents 这一类项目关注的持久化、记忆、文件和恢复，作用就在这里。上下文变长有帮助，把所有材料一直塞在同一个窗口里却不是唯一办法。重要信息放在哪里、下一轮能不能找回来，会直接影响任务能否继续。

多模态在扩展任务能接触的世界。 从读图、听声音到理解视频和界面，模型能利用的证据与行动入口都在增加。Google DeepMind 的模型体系也把多模态与不同应用方向放在一起。但看到界面、生成一段视频，与稳定控制真实业务，仍然不是同一种能力证明。

这些方向会互相帮助，最后共同表现为“用户少做了多少工作”。一个更强的模型，如果被装进只能回答文字的产品里，执行能力仍然出不来；一个工具极多的平台，如果模型不能判断结果，用户也还是得守在旁边。

怎样才算走到“中间不用我干预”

独立评测能提供一个提醒。METR 的任务时间跨度说明把难度与人类完成任务所需时间联系起来，并同时展示不同成功概率下的时间跨度。页面标注的数据更新时间是 2026 年 9 月 8 日；所谓 50% 时间跨度，不是“模型已经可以稳定无人值守工作这么久”。

一次漂亮的演示，很容易把成功的那一半拍下来。真正每天使用时，还得处理剩下的那一半：工具中断了、文件写错了、网页换了、任务跑到后面忘了前面的约束。

我不认为“现在还会出错”足以挡回用户的期待。用户已经给出可以核对的目标，普通报错和环境障碍就应该尽量由系统消化。需要停下来的，应当是缺少关键事实、目标确实冲突，或下一步超出授权。

也正因此，最能打动我的产品展示，不是从一句话里变出多少节点，而是它怎样处理一个没按预期发生的结果：会不会重新读取，能不能修复，会不会打开自己生成的文件检查，最后能否说清楚做完了什么、还差什么。

工作流会继续存在，许多确定规则也值得继续保留。但用户应该越来越少被要求担任整个系统的运行时。

我把任务交出去，是希望少操一份心。至于产品内部怎样调度，只要它能解释、能恢复、能把结果交出来，那些复杂性就应该由产品自己承担。
