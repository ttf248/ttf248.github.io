Codex 写不好界面时，我先让 ChatGPT 画 UI 稿

这次卡住的不是代码能力，而是界面目标太虚。strategy_studio 前面一直在推进业务逻辑：Yahoo 行情、PostgreSQL、异步回测任务、报告和研究工作台都在往前走，但一开始没有 UI 稿，后面再让 Codex “允许破坏性重构、重新设计 UI 和交互逻辑”，效果还是容易在旧结构里打转。真正变顺，是先在 ChatGPT 网页端把 UI 设计稿做出来，再交给 Codex 按图还原。

这个过程有点反直觉。平时写代码，我会直接把目标扔给 Codex：改模块、补测试、跑验证、提交。到了前端重构，尤其是已经有一套业务逻辑和旧界面的项目，纯文字提示词很容易变成“在原来的格子上重新摆一遍”。你可以继续加形容词：元素不要太密集、适配 24 寸和 32 寸、聚焦核心功能、允许大改、不要保守。但模型看到的仍然主要是现有代码结构，它会优先沿着现有组件、路由和样式惯性往下改。

strategy_studio 正好是这种项目。README 里写得很清楚，它已经不是一个单点脚本，而是中文优先的策略研究平台：Next.js 前端、FastAPI API、PostgreSQL、Worker、Scheduler 和 Yahoo 同步链路一起跑。前端 README 也把页面收敛成一个研究工作台：样本准备、实验配置、任务跟踪、结果复盘、模板维护，还有报告详情和运行维护入口。业务对象很多，状态很多，用户真正要看的路径也很多。

这种界面如果没有先做视觉规划，后面很容易陷入两个问题：一是代码层面的“页面都能用”，不等于视觉层面的“用户知道先看哪”；二是提示词说的“更好看”没有验收物，Codex 每次重构都只能猜审美。

卡住的地方不是提示词不够狠

我一开始也没有怀疑 Codex。因为后端、数据链路、报告落库、前端 API 对接这类任务，它都能按工程方式推进。真正不太行的是“重新设计 UI”这个目标本身太宽。

允许破坏性重构，看起来给了模型自由度，实际还缺一个更关键的东西：判断锚点。前端不是只有功能关系，还有密度、留白、视觉层级、颜色气质、信息先后、按钮权重和大屏适配。文字可以描述这些要求，但文字不会自动生成一个统一的版面语言。尤其当旧代码已经存在时，Codex 会天然把“重构”理解成在现有页面里调整组件，而不是先退回到产品设计层重新排布。

我白天出去一趟，晚上突然想到的转折点是：不要继续在 Codex 里让它猜 UI，先去 ChatGPT 网页端让图像模型画一组 UI 稿。OpenAI 的帮助页本来也把 ChatGPT Images 定位成可以在对话里生成和编辑图片的能力，这个入口更适合做视觉探索。它不需要直接改代码，所以可以先把业务信息变成图，而不是在旧组件里妥协。

当时用的核心提示词很直接：

https://github.com/ttf248/strategy_studio 分析当前项目的前端代码，理解业务逻辑，作为专业的UI设计师、交互设计师，帮我重新设计一套前端页面，每个页面单独出图，记得适配 24寸、32寸显示器，元素不要太密集，方便用户使用聚焦核心功能。

这一步出来的效果已经比在 Codex 里直接重构强很多。原因不神秘：图像生成先交付的是“目标长相”，它把抽象要求压成了版面、颜色、模块比例和视觉节奏。Codex 后面再接手时，不再需要猜“高级一点”“不要太密集”到底是什么意思，而是可以围绕一张图去还原布局。

不是简单的“智力阉割”

后来我又去翻了一圈官方说明。更准确的解释不是“网页版 ChatGPT 更聪明，Codex 被阉割”，而是两个入口服务的任务形态不同。

OpenAI 对 Codex CLI 的定义是本地终端里的 coding agent，可以读、改、运行当前目录里的代码；Codex web 则是在云端环境里读写代码、后台跑任务。OpenAI 讲 Codex agent loop 的文章也把重点放在 agent harness：模型推理、工具调用、上下文管理、文件读写和命令执行一起构成一次软件任务。也就是说，Codex 的优势不是凭空出设计稿，而是把“目标、上下文、工具、验证”串起来，交付可落地的代码改动。

ChatGPT Images 走的是另一条路径。OpenAI 帮助页明确说，ChatGPT 可以在对话里创建和编辑图片，也可以生成 mockup 或创意视觉。这个产品入口天然把输出目标放在图像上，用户可以先围绕配色、构图、密度和视觉层级来回调，而不必马上落到 CSS、组件拆分和回归测试。

所以，这次体验里真正的差异不是模型有没有“少一块脑子”，而是我给两个入口的任务不同。把“重新设计 UI”直接丢给 Codex，它会站在代码仓库里思考：哪些组件要改、哪些文件要动、怎么避免破坏现有业务逻辑。把同一段业务背景先丢给 ChatGPT Images，它会先交付一张可见的目标图。前者更像工程还原，后者更像视觉探索。没有 UI 稿时，Codex 很容易在旧界面里局部优化；有了图以后，Codex 才能把图当成验收标准。

这里还有一个容易忽略的点：官方的 Codex prompting 文档也强调，提示词要给 Codex 可用的上下文，例如相关文件和图片；Goal mode 也需要清楚的完成标准。换句话说，设计稿不是绕开 Codex，而是在给 Codex 补足它最需要的上下文和验收条件。我的问题不是“Codex 不能做 UI”，而是我一开始要求它同时完成产品设计、视觉探索和工程实现，验收目标却只有几句审美描述。

先把审美也变成材料

第一轮仍有问题：默认配色偏常规蓝白，不太符合我的审美。这个时候如果直接把“不喜欢蓝白”丢给 Codex，仍然会回到文字猜测。更有效的做法是先在网页里继续沟通配色，把色彩方向聊成一个可见方案，再让图像模型按配色出示意图。

这张就是最初那版蓝白配色的效果。它已经解决了“页面怎么排”的问题，但色彩气质还是偏常规后台系统，和我想要的研究工具感不完全一致。

这一步其实是在补“设计系统”的最小版本。不是正式 Figma，不是完整组件库，但已经把前端重构最容易漂移的几件事定住了：底色气质、强调色、卡片层级、图表和操作区的关系、页面在大屏上如何呼吸。

后面结合前面的业务提示词，就拿到了现在仓库里的 ui 目录。里面不是一张总览图，而是按页面拆开的设计稿：首页、行情研究、回测实验、报告中心、报告详情、策略模板、运行维护。这个拆分很重要，因为 strategy_studio 的前端不是营销页，而是一个研究工具。首页要承接工作流，行情页要让价格、宏观和指标能同时观察，报告详情要让结果、曲线、输入和重跑路径连起来。每个页面单独出图，Codex 才不会把所有目标挤在同一张“大而全首页”里。

图出来以后，Codex 的角色就变了。它不再是“从零当 UI 设计师”，而是“理解现有业务逻辑，按视觉目标改代码”。这更接近它擅长的工作：拆组件、调整路由、改 CSS、对齐交互状态、跑 lint/build、处理破坏性重构后的回归。

Codex 需要目标，不需要包办所有前置工种

这次让我重新确认了一件事：AI 编程不是把所有工种都塞进同一个对话框。Codex 可以写代码，也可以做相当多的产品判断，但当任务核心是视觉探索时，把它放在代码仓库里直接猜，未必是最省力的路径。

更顺的链路应该分成三段。

第一段，在 ChatGPT 网页端做视觉探索。让它读仓库、理解业务、单页出图，再针对配色、密度和大屏适配反复改。这个阶段的产物不是代码，而是设计稿。

第二段，把设计稿和约束交给 Codex。提示词不要再停在“重新设计 UI”，而是要写清楚：以哪些图片为目标，哪些业务逻辑不能破坏，哪些页面可以破坏性重构，哪些测试和构建必须通过。目标越像验收标准，Codex 越能稳定工作。

第三段，进入工程还原。这里才适合让 Codex 开 goal 或连续任务模式：先读前端结构，再按页面拆分实施，每个页面完成后跑验证，最后统一检查交互和响应式。goal 的价值不在于让模型突然有审美，而在于让它围绕明确目标持续执行。

我以前容易把“提示词写得更狠”当成解决办法。现在看，前端重构里更有用的不是狠，而是把缺失的中间产物补上。没有 UI 稿时，破坏性重构只是拆得更大；有了 UI 稿以后，破坏性重构才有方向。

这套流程也不是只适合 strategy_studio。任何已经有业务逻辑、但前端长期靠边做边补的个人项目，都可以这么处理：先让图像模型把界面目标画出来，再让 Codex 把目标变成代码。模型之间不是谁替代谁，而是各自接自己更像工种的那一段。

写作思路摘要

这篇保留了真实过程里的三个转折：先写业务导致 UI 没规划，在 Codex 里继续加重构提示词效果有限，最后改成先用 ChatGPT 网页端出设计稿再交给 Codex 还原。后续更新补了一层官方资料核对：我没有把体验写成“某个入口智力更高”，而是把它收束为产品形态、工具链、上下文和验收物不同。
