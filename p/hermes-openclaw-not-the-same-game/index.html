Hermes 与 OpenClaw 深度对比：架构分叉，以及 Token 账单差在哪

从 Gateway 与 Agent Core 的底层差异，看谁把上下文前置、谁把成本后置

2026年04月15日 · 阅读时长: 5 分钟 · Gemini 4 · blog-writer-free v1.2.0
English 日本語
分类

把 Hermes 和 OpenClaw 放在一起比，很多人第一反应是问“Hermes 能不能平替 OpenClaw”。其实这个问题一开始就问偏了。

它们确实都在做个人 AI 助手，甚至 Hermes 官方都内置了 hermes claw migrate 迁移命令，但两者的骨架完全不是一回事：OpenClaw 是从常驻通信网关（Gateway）往外长的个人助理系统，把上下文前置；Hermes 是从本地 Agent 内核（AIAgent）往外长的自托管平台，把上下文后置。 这个底层分叉，直接决定了它们的功能气质和 Token 账单。

一、架构分叉：Gateway 主角 vs Agent Core 主角

  • OpenClaw（Communication-first）：核心是一个长期在线的单一 Gateway，独占 Telegram、Discord、Slack、WhatsApp、Signal、WebChat 等消息面，控制面、Web UI 与节点全通过 WebSocket 接入。它优先解决“存在感与组织边界”——DM 配对、群聊路由、多账号身份、delegate 授权写得极其细致。
  • Hermes（Agent-core-first）：CLI、Gateway、ACP、Batch Runner、API Server、Python Library 全部只是入口，最终汇入同一个 AIAgent 内核（底层 SQLite + FTS5 存会话）。它的重心不在消息路由，而在能力沉淀——渐进式披露的 skills（兼容 agentskills.io，Agent 自己可增删改）、可插拔记忆后端、MCP 工具集，甚至顺手支持 trajectory 导出与 RL 训练。

二、Token 账单差在哪：固定盘前置 vs 按需展开

架构差异落到账单上，就是两套完全不同的成本结构：

对比维度 OpenClaw Hermes
默认形态 长期在线、多渠道个人助理工作台 本地工作流与自托管 Agent 内核
上下文策略 前置注入：AGENTS.md、SOUL.md、USER.md、IDENTITY.md、TOOLS.md、MEMORY.md 随 session 在场 后置按需：项目上下文按路径 first match wins 发现，Skill 先给轻量索引，用到再展开
Prompt Cache 友好度 固定底座偏厚，心跳（HEARTBEAT.md）与多渠道规则容易拉高基础消耗 起步极轻，系统提示词克制，更容易保住缓存命中
隐藏风险 固定盘不控制好会持续烧基础 Token 复杂任务一旦展开大量记忆、子 Agent 和长工具输出，照样烧钱

所以“谁更省 Token”不能脱离场景硬答：如果你要养一个跨五个聊天软件、长期在线、有鲜明人格边界的助理，OpenClaw 把上下文前置是合理的产品代价；如果你主要在本地仓库跑代码、沉淀可复用 Skill、接 MCP 工具，Hermes 把“眼下用不到的东西先挡在上下文外面”的设计，起步账单确实更好控。

三、怎么选？别问平替，问你在养什么

  • 想要长在消息网络里的常驻 AI 助理（重渠道、账号、路由与组织边界）→ 选 OpenClaw；
  • 想要长在本地工作流里的可进化 Agent 平台（重 Skill 沉淀、按需上下文、MCP 与可扩展内核）→ 选 Hermes（如果在本地部署 Hermes 遇到搜索出站稳定性问题，可结合Hermes 搜索不稳：SearXNG 出站交给 Mihomo）。

真要算账，别靠体感——用 OpenClaw 的 /context detail、/usage tokens 或 Hermes 的实际 provider 账单盯紧真实消耗。决定账单厚薄的，往往不是框架名字，而是你写了多长的 SOUL.md、塞了多少冗余记忆、以及有没有把工具输出收住（长 Agent 缓存计价变化可对照GPT-6 降价后 Claude 还值高价吗）。
