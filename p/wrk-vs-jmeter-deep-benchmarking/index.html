HTTP 压测选 wrk 还是 JMeter

在给 HTTP 服务做压力测试时，工程团队最常遇到的两款工具就是 wrk 和 JMeter。

很多人对它们的印象很直观：wrk 偏向用一个线程扛多条连接猛轰接口，而 JMeter 更常见于短连接测试，当然也能通过配置改成长连接。这个直觉抓住了表象，但真到架构选型和排查发压瓶颈时，决定两者行为差异的其实是底层并发模型与设计目标。

底层架构：事件驱动复用 vs 一用户一线程

为什么 wrk 开 4 个线程就能把被测服务器的网卡打满，而 JMeter 开几千个并发用户时，往往发压机自己先 CPU 飙红甚至内存溢出？根源在于并发模型的不同。

  • wrk（C + LuaJIT + 事件驱动）：采用与 Nginx 类似的非阻塞 I/O 多路复用（Linux 下为 epoll，macOS/BSD 下为 kqueue）。只需开启与 CPU 核心数相当的少量线程，每个线程内部通过事件循环同时管理成百上千条 TCP Socket。几乎没有线程上下文切换开销，把发压机算力全部集中在发包与收包上。
  • JMeter（Java + 传统多线程模型）：采用“一个虚拟用户对应一个 JVM 线程”的阻塞式模型。模拟 2000 个并发用户，就需要创建 2000 个操作系统线程。线程栈占用大量内存，高频上下文切换叠加 JVM GC 停顿，导致单台发压机的吞吐上限远低于 wrk。

长连接还是短连接？先破除一个常见误解

严格来说，JMeter 并不是默认强制走短连接。

在 JMeter 的 HTTP Request 采样器中，Use KeepAlive 默认是勾选的。只要服务端不主动断开，同一个线程在连续循环发请求时默认也会复用连接。

之所以实战里很多人觉得“JMeter 跑起来像短连接”，通常来自三种情况：

  1. 高线程数、低循环次数的配置：开了很多线程，但每个线程只跑一两轮就结束，或者中间设置了较长的思考时间（Think Time）触发服务端 keepalive_timeout，实际效果就变成了高频 TCP 建连。
  2. 刻意取消 Use KeepAlive：测试网关或负载均衡的新建连接能力（CPS）时，会主动关掉 KeepAlive，模拟海量独立用户的短连接风暴。
  3. 发压机端口耗尽：一旦切入高频短连接压测，Linux 客户端的临时端口很快会被大量 TIME_WAIT 连接占满，没等服务端撑不住，发压机自己先报错。

反观 wrk，它天生就是为 HTTP/1.1 Keep-Alive 极致长连接复用设计的：启动后建立 -c 条连接，全程死死复用，压出的是被测接口在理想连接状态下的纯处理天花板。

核心维度对比

对比维度 wrk JMeter
底层实现 C + LuaJIT（epoll / kqueue 事件驱动） Java（JVM 多线程，一虚拟用户一线程）
单机发压能力 极高，单机轻松打出数万至数十万 QPS 偏低，大并发需多机分布式压测（Master/Slave）
连接模型偏好 天生极致长连接复用（Keep-Alive） 默认 Keep-Alive，可灵活切换短连接模拟建连风暴
业务编排能力 较弱，依赖 Lua 脚本做轻量动态参数化 极强，支持登录鉴权、关联提取、条件分支、复杂断言
协议生态 专注 HTTP / HTTPS HTTP、WebSocket、JDBC、TCP、Kafka、gRPC 等
报告输出 简洁终端摘要（QPS、平均延迟、分位数） 完整 HTML 报告、趋势曲线与监控插件

选型怎么落？两把工具各司其职

优先用 wrk 的场景
  • 单接口极限摸底：测网关、缓存层、无状态微服务的纯 QPS 上限。
  • 快速性能回归：对比某次代码改动或连接池调优前后的延迟与吞吐变化。
  • 资源受限：只有一台普通发压机，不想搭复杂的分布式压测集群。
优先用 JMeter 的场景
  • 复杂业务链路：登录拿 Token → 查余额 → 下单 → 校验状态的串行流程。
  • 精细结果校验：需要对响应 JSON、业务错误码甚至数据库落库做严格断言。
  • 真实流量模拟：需要模拟思考时间、阶梯加压或大量陌生用户的短连接建连。

压测时最容易踩的两个坑

  • 把发压机瓶颈当成服务端上限：QPS 上不去时，先检查发压机自身的 CPU、内存、网卡和 TIME_WAIT 状态。使用 JMeter 正式发压时，务必切到非 GUI 命令行模式（-n -t ... -l ...），开着图形界面跑压测会消耗掉大量本机资源。
  • 忽视“协同遗漏（Coordinated Omission）”：原版 wrk 在服务端突然卡顿（如触发 Full GC 或锁等待）时，发压线程会等上一个请求返回再发下一个，导致报告里的 P99 延迟比真实用户体感乐观得多。若对长尾延迟高度敏感，建议改用恒定吞吐率发压的 wrk2 或 k6。

压测的目的从来不是刷出一个好看的峰值数字，而是把隐蔽的并发短板——比如连接池打满、线程池饥饿，或是像MySQL 间隙锁死锁这类低并发下根本复现不了的故障——提前在上线前打出来。把 wrk 当手术刀测单点极限，把 JMeter 当沙盘演练完整业务流，配合着用才最稳妥。
