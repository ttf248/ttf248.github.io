AI 写博客这件事，为什么最后还是得做成工程

去年写了不少 AI 稿子，最土的流程是：先自己列大纲，让聊天框吐出正文，再手动复制到本地 Markdown，挨个补 title、date、slug、tags、`

  2. 二、把消费侧和生产侧拆开：从 2000 次调用压到 5 次

  4. 四、后续演进：模型变强后，工程也要学会做减法

` 和参考资料。

真正磨人的从来不是写正文，而是正文外面那一圈机械重复劳动。当命令行编程 Agent 已经能直接读写仓库文件时（交互迁移见基于命令行的 AI 编码交互），如果写博客还停留在“网页复制粘贴”，工具的腿其实是被自己绑住的。

此前把这套博客工程的演进拆成了三篇，现在合回一篇完整复盘：从 blog-writer 写死发布契约，到 blog-style-suite 拆开风格学习与 Token 成本，再到本地与在线模型按工位分工，最后走到更轻量的 blog-writer-free。

一、第一步不是学文风，而是把发布契约写死

blog-writer 最早长出来，核心价值不是“AI 学会了我的文风”，而是把写稿从玄学 Prompt 变成了可重复执行的固定工序：

  • 输入必须有明确问题和事实锚点；
  • 输出必须是带完整 frontmatter、<!--more-->、参考资料与原始提示词附记的 Hugo 成稿，直接落盘到 content/post/；
  • 系列文章自动处理时间戳递增和 relref 站内跳转。

Prompt 天生漂移，写进 Skill 契约和校验脚本后，元信息、格式与可追溯性才不再靠人眼兜底。

二、把消费侧和生产侧拆开：从 2000 次调用压到 5 次

自动化跑顺后，很快撞上了第二堵墙——Token 墙。想让模型学自己过去的写法，最偷懒的办法是每次写稿都把几十篇历史文章塞进上下文。单次能跑，长期必炸：Token 费线性暴涨，噪音稀释注意力，写稿和风格维护彻底缠死。

解法很像经典的软件架构：把“风格生产侧（blog-style-suite）”和“写稿消费侧（blog-writer）”彻底解耦。

  • 生产侧做成独立 Python 流水线（scanner.py / builder.py / compressor.py）：先纯启发式扫描和评分（0 次 AI 调用），再按 technical / finance / essay / tooling 四个赛道批量精选与压缩，把冷启动 AI 调用从约 2000 次硬压到每个 provider 最多 5 次，并加指纹缓存防重复烧钱；
  • 消费侧只读最终发布的轻量 published.runtime.json，专注把当下这篇写好。

三、本地、在线与多 Provider 分工：别让旗舰模型干脏活

流水线拆开后，模型分工自然水落石出（与低成本模型该接的活是同一套逻辑）：

本地模型：生产侧体力层
  • 如 LM Studio 跑 Gemma 4 26B A4B（实测见Gemma 4 本地部署）。
  • 承担反复扫描、多轮风格压缩试错与配置重算，跑得起、跑得勤。
在线旗舰：消费侧收口层
  • 负责联网核验事实、长上下文推演与最终成稿收口。
  • 多 Provider 走同一套发布契约，不被单一厂商绑死。

四、后续演进：模型变强后，工程也要学会做减法

走到 2026 年底，这套工程又往前迈了一步：随着新一代模型本身推理与写作能力大幅提升，过度繁琐的机械流水线反而容易把文章写得像“八股模板”。于是又长出了更轻量的 blog-writer-free——写作时放开手脚、只盯真实问题和个人判断，成稿后再跑轻量格式化、站内互链与 Hugo 构建校验。

这恰好印证了大模型进化之后，谁还要替 AI 画工作流里的判断：工程化不是把流程越画越复杂，而是把该固化的脏活锁进脚本，把该留给思考和表达的空间还给模型和人。
